# Phase 0 — Scope & Safety

This document records the Phase 0 decisions for the Multilingual AI Legal Assistant: jurisdictions, document scope, PII handling, UI disclaimers, and annotation guidelines. It is intended as the authoritative reference for data collection, annotation, and early product safeguards.

---

## 1) Jurisdictions & Document Types (initial)

Start narrow and expand:

- Primary jurisdiction: India (national laws)
  - Core statutes: Indian Penal Code (IPC), Code of Criminal Procedure (CrPC)
  - Selected Sections/Acts relevant to FIRs and criminal procedure
  - Central government rules and national-level criminal case law summaries
- Secondary: State-level rules (add state-specific laws when required)
- Languages: English and Hindi first; plan for Indic languages (Tamil, Telugu, Marathi, Bengali, Kannada, Malayalam, Gujarati) progressively

Document types to include initially:
- Statutory text (IPC/CrPC sections)
- Short extracts of case law (headnotes / summaries) where public domain
- Sample FIR text (annotated, synthetic and anonymized real examples)
- Sample police forms and templates
- Common contract templates for contract review feature (sample agreements, clauses)

Notes:
- Prefer authoritative sources (government websites, published law reports) for statutes and case law.
- Track source and version (statute version, date) as metadata for every document.

## 2) PII / Sensitive Data Handling

Principles:
- Minimize collection: Only collect PII when strictly necessary for the task.
- Redact by default: Remove or obfuscate PII fields in stored training data and logs unless explicitly consented.
- Encrypt at rest & in transit: Use secure storage for any sensitive artifacts.
- Access controls: Limit access to raw PII to a small, audited group of annotators under NDA.

Examples of PII to treat specially:
- Names of private individuals (victims, witnesses, accused)
- Phone numbers, email addresses
- Physical addresses and precise GPS/pincode data
- National identifiers (Aadhaar, passport, driver's license)

Redaction rules (minimum):
- Replace names with placeholders: `[PERSON_1]`, `[PERSON_2]` preserving relative references (victim vs accused).
- Replace phone numbers with `[PHONE]`, emails with `[EMAIL]`, Aadhaar with `[ID]`, pincodes with `[PINCODE]`.
- Remove or generalize precise addresses to locality only (e.g., `Mahatma Gandhi Road, [CITY]`).

Consent & retention:
- Do not use data containing PII for public release unless explicit legal permission is documented.
- Keep an audit log of who accessed raw PII and why.
- Define retention periods (e.g., raw data removed after annotation + QA + model training unless needed and justified).

## 3) Legal Disclaimers & UI Guidance (required)

Add a clear, visible disclaimer in the UI (home, incident reporter, FIR preview) and in generated outputs (PDF header or footer). Example text (English):

"Important: This assistant provides informational, non-binding legal guidance only. It does not replace professional legal advice or official police procedures. Any FIR draft generated by this system must be reviewed and validated by a qualified human (police/legal professional) before filing. The system may be imperfect and can produce errors or omissions — use caution and verify against authoritative sources."

Short notice for input forms (near text area):

"Do not submit sensitive personal identifiers unless necessary. Personal data will be redacted in stored examples where possible." 

Add an acceptance checkbox for critical actions (for example before allowing export/download of FIR PDF):

"I understand this FIR draft is advisory only and I will review it with a qualified professional before use." (must be checked to proceed)

## 4) Annotation Guidelines (entities, clauses, severity)

Purpose: create consistent labels so NER and clause classifiers can be trained reliably.

4.1 Entity Annotation

- Entities to annotate (initial):
  - PERSON — people (victim, accused, witness). Use placeholders in exports.
  - LOCATION — place names, localities, roads, cities, districts, states.
  - DATE — dates in any common format (dd/mm/yyyy, dd-mm-yyyy, Month dd, yyyy).
  - TIME — explicit times (10:30 PM, 22:30).
  - SECTION — mentions of legal sections (e.g., `IPC 379`, `Section 302`), include numeric and textual forms.
  - ORGANIZATION — police stations, courts, govt agencies.
  - IDENTIFIER — phone numbers, emails, Aadhaar/passport numbers — annotate but mark as sensitive for redaction.

Annotation rules:
- Use longest-match for multi-token entities ("Rahul Kumar Singh" = single PERSON entity).
- Preserve casing and original text in annotation metadata but store redacted text in training exports.
- For ambiguous tokens, prefer human QA and consensus — add an 'uncertain' flag if annotator is unsure.

4.2 Clause Annotation (for contract review)

- Clause-level labels (initial):
  - OK — standard clause with no immediate concern.
  - FLAGGED — clause contains concerning language (penalty, unilateral amendment, indemnify without limits).
  - HIGH_RISK — clauses that are likely harmful (no liability, indefinite indemnity, immediate forfeiture, waiver of fundamental rights).

Annotation guidance:
- Split contract into logical clauses by numbering, semicolons, or natural sentence boundaries.
- For each clause, label the primary status and zero or more reason tags: `penalty`, `indemnity`, `no_refund`, `unilateral_change`, `arbitration_only`, `waiver`.

4.3 Severity and Confidence

- Annotators must assign a confidence score (low/medium/high) for each label.
- Use adjudication: multiple annotators per sample (2 annotators + 1 adjudicator) for high-quality labels.

4.4 Example annotations (JSONL line toy examples)

1) FIR example (NER):
```
{ "id": "fir_001", "text": "On 12/05/2024 at 10:30 PM, Rahul Kumar reported his bike stolen near MG Road, Bangalore.", "entities": [{"type":"DATE","span":"12/05/2024"},{"type":"TIME","span":"10:30 PM"},{"type":"PERSON","span":"Rahul Kumar"},{"type":"LOCATION","span":"MG Road, Bangalore"}], "pii_redaction": true }
```

2) Contract clause example (clause classification):
```
{ "id": "contract_001_clause_3", "clause": "The Company may change these Terms at any time without notice.", "label": "FLAGGED", "reasons": ["unilateral_change"], "confidence": "medium" }
```

## 5) Operational & Legal Controls

- Enforce NDAs and role-based access for annotators handling raw PII.
- Keep an annotation audit trail (who labeled what and when).
- Maintain a human-in-the-loop review workflow for any FIR draft before export or persistent storage.
- Create a takedown & correction policy for users who request removal or correction of personal data.
